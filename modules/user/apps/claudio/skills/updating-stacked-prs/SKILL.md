# Updating Stacked PRs

## Overview

A stacked PR chain (`trunk -> A -> B -> C`) only stays clean if every branch's
diff is computed against its *actual* base, and that base is never missing a
commit the branch itself already has. GitHub computes a PR's diff via
merge-base with its declared base branch — if the base is stale, the diff
silently balloons to include content that already landed elsewhere, and looks
to a reviewer like the PR is touching files it has no business touching.

Core principle: **sync bottom-up, one hop at a time, never skip a link.**
Merging trunk directly into a non-root branch is the single most common way
this breaks — it makes the non-root branch race ahead of its own base, and
the base's now-missing commit reappears as a stray file in that branch's PR
diff.

## When to Use

- Before pushing for review on any branch in a stack, if its base branch has
  moved.
- Right after fixing a Copilot/human review comment on one PR in the stack —
  that fix needs to propagate to everything stacked on top of it.
- When a PR's GitHub diff (`gh pr view <n> --json files`) shows a file that
  has nothing to do with the change — this is the direct symptom of a stale
  base somewhere below it in the chain, not a bug in that PR's own commits.
- When GitHub's "rebase stack" stops on a branch, or a stack shows in the PR UI as a native GitHub stack. Skip the merge-based guardrails below and go straight to "GitHub Stacked PRs".
- Not for: a single, unstacked branch (there's no chain to walk) or a stack
  you're building for the first time (this is about *maintaining* one).

## Guardrails

Guardrails 2 and 3 are the merge flow, for stacks GitHub does not track natively. For a native GitHub stack, guardrails 1, 4 and 5 still apply, and "GitHub Stacked PRs" below replaces 2 and 3.

1. **Confirm the real stack order before touching anything.** Don't assume
   from memory or from a note — a base can get retargeted automatically
   (GitHub does this when a lower PR merges) or by a teammate. For every PR
   in the suspected chain:
   ```
   gh pr view <n> --repo <org>/<repo> --json baseRefName,headRefName
   ```
   Build the actual order from `baseRefName`/`headRefName`, and find the
   root — the one branch whose base is the trunk (`development`, `main`,
   whatever). Everything downstream of a wrong assumption here is wasted
   work.

2. **Merge the trunk directly into the root branch only.** Every branch above
   the root gets updated by merging its *immediate parent in the stack*,
   never the trunk directly. If you need to land a trunk commit that only the
   root is missing, merge it into the root, then walk it up hop by hop — do
   not shortcut by merging trunk into a branch in the middle. That shortcut
   is exactly what desyncs the branch from its declared base and produces
   the stray-file symptom above.

3. **One hop, full verification, before the next hop.** For each branch,
   in order from the root to the tip:
   - `git fetch origin` (the trunk, if this is the root; otherwise the
     immediate parent branch)
   - `git merge origin/<parent>` — resolve any real conflicts; watch for
     recurring merge artifacts in generated/autogenerated files (schema
     dumps, lockfiles) that don't show up as a `CONFLICT` line but still
     leave the file wrong (e.g. a duplicated column definition git couldn't
     line up because the two sides inserted it at different positions) —
     diff the file's logical content, not just check for conflict markers
   - run the test suite and linter for the affected area, confirm green
   - `git push origin <branch>` — if the push is rejected or the remote has
     moved unexpectedly, `git fetch` and `git merge` again (some repos run a
     bot that auto-syncs open PR branches with trunk on its own schedule,
     creating independent merge commits on the remote); never force-push to
     resolve this, just merge the divergence like any other
   - only now move to the branch that sits on top of this one

4. **Verify every PR's diff after the whole stack is pushed**, not just the
   one you started from:
   ```
   gh pr view <n> --repo <org>/<repo> --json mergeable,additions,deletions,changedFiles,files
   ```
   Confirm the file list for each PR contains only what that PR's own
   commits actually touch. A clean diff on the PR you were fixing does not
   mean the rest of the stack is clean — verify each one.

5. **If a stray file still shows up after a sync, the fix is never in the
   branch where you noticed it.** Trace *down* the chain: check whether the
   branch's declared base itself is behind trunk (or behind its own parent).
   Fix the root cause at whichever branch is actually missing the commit,
   then re-propagate upward through every branch above it — the same
   symptom can appear on more than one PR in the stack simultaneously if the
   root itself is what's stale. Checking only the branch where the symptom
   surfaced and calling it fixed is the mistake that causes rediscovery of
   the same issue one link further up.

## GitHub Stacked PRs (stack shown in the PR UI)

The merge flow above breaks a stack that GitHub tracks natively. Its "rebase stack" button replays commits one by one and stops at the first branch with a merge commit in its history (observed twice on safxgroup/saf in October 2026; unverified against GitHub's docs). Rebase instead of merge, at every hop, and keep every branch linear.

For each branch, from the root to the tip:

1. Check the worktree is clean and has nothing unpushed: `git -C <worktree> status --short` prints nothing, and `git -C <worktree> log --oneline origin/<branch>..<branch>` prints nothing. If either prints something, stop and ask.
2. Save the tip: `git -C <worktree> branch -f backup/<branch>-pre-rebase <branch>`.
3. Find the old parent tip, the commit the branch currently sits on. If you moved the parent yourself, it is `backup/<parent>-pre-rebase`. If GitHub's UI moved it, find it in `git -C <worktree> reflog origin/<parent>` (the entry before the latest fetch), or check that `git merge-base <branch> origin/<parent>@{1}` is the parent's old tip.
4. Rebase: `git -C <worktree> rebase --onto origin/<parent> <old parent tip> <branch>`. For a fixup, use `GIT_SEQUENCE_EDITOR=: git -C <worktree> rebase -i --autosquash origin/<parent>`: the agent shell has no interactive editor.
5. Compare the commit series: `git -C <worktree> range-diff <old parent tip>..backup/<branch>-pre-rebase origin/<parent>..<branch>`. Every line should be `=`. A `!` line means a commit changed: read it before going on. As a second check, the branch's own patch, old against new, should match: `diff <(git diff <old parent tip> backup/<branch>-pre-rebase | grep -v '^index ' | grep -v '^@@') <(git diff origin/<parent> <branch> | grep -v '^index ' | grep -v '^@@')` prints nothing.
6. Run the tests and linter for the affected area.
7. Ask for approval to force-push this branch, naming the branch and the old SHA. An open PR does not cover a force-push.
8. Push: `git -C <worktree> push --force-with-lease=<branch>:<old sha> origin <branch>`. Only then move to the branch on top.

Rules that hold the whole time:

- Never `git pull` a stack branch. After a UI rebase, run steps 1 and 2, then `git -C <worktree> fetch origin` and `git -C <worktree> reset --hard origin/<branch>`, and ask before the reset. An IDE pull (`pull --ff`, whatever `pull.rebase` says) merges the old history back in. The push then goes out as a plain fast-forward, and the next "rebase stack" stops on that branch again.
- A fix made inside a merge resolution disappears on rebase, because the merge commit is never replayed. Step 5 is what catches it. Re-add it with `git commit --fixup=<sha>` and the autosquash form in step 4.
- Don't pin SHAs in notes, plans or PR descriptions. Every UI rebase rewrites all of them. List commit titles and the `git log` command that prints the current SHAs.

## Worked example

Stack: `development -> em-bic-check (#A) -> em-bic-resolver-real (#B) ->
em-bic-write-path (#C)`. `#A`'s base had drifted 2 commits behind
`development`. Syncing only `#B` and `#C` against their immediate parents
made their own diffs look clean at the time, but both PRs still showed 3
unrelated frontend files — because `#A`, the root, was still missing those 2
commits, and `git merge-base` between any downstream branch and `#A` didn't
include them either. The actual fix: merge `development` into `#A` first,
push, then merge the updated `#A` into `#B`, push, then merge the updated
`#B` into `#C`, push — verifying tests and the diff at every hop. Only then
did both `#B` and `#C`'s GitHub diffs stop showing the stray files.
